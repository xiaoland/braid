# 工作边界与共同材料的作用

工作项使一位负责人能够推进一个可被采用的结果。结果可以是决定所需的调查、可复用接口、完整用户操作或实现候选。若一个状态的修改与后续观察分别属于几项工作，局部交付可以各自成立，整体结果却可能没有汇总责任；分工数量并不能说明责任已经完整。

## 内聚结果与真实依赖

独立负责人、可独立采用的成果或不同结束条件，是分开工作的实际理由。已有工作能承接新增结果时，其目标与完成条件决定承接是否成立；名称相近或引用同一接口不足以说明范围相同。父子与 PR 关联保存组织和来源，实际责任与采用各需自己的依据。

业务能力有自己的需求解释、技术取舍、验收与后续协调时，父项建立并指派业务子 Issue，说明完整结果、适用材料和共同前提；负责人据此形成方案，再组织关联实现 PR。实施独立业务能力之前，需要先安置这项结果责任。已有 Issue 能完整承接的局部改动，可以增加关联 PR，无需为每个场景、文件或 PR 新建 Issue。实现候选完成不会解除关联 Issue 尚未兑现的要求；父项继续核对跨能力约束与整体结果。

例如账户管理与文件导入共享持久化设施。父 Issue 的基础 PR 可以先统一 schema 和共同接口，再顺序推进两项业务 Issue 的实现 PR；业务负责人分别持有需求、方案与验收，父项核对跨入口结果。共同文件的冲突影响实施与合并顺序，不决定业务责任是否拆分。前提尚未交付时，也可以先建立业务 Issue、明确范围和负责人，让依赖该前提的实施动作等待。

先判断哪些成果可以分别交付和取得反馈，再安排它们何时执行。顺序执行没有消除不同成果的边界；并行也没有自动建立独立性。分开能缩小各负责人的相关上下文，合并能减少必须反复共同裁决和交接的语义；判断应指出具体受益的成果或具体无法分开的条件，不能仅以“协调成本高”结束比较。

共同前提与消费它的业务能力各有完成依据。例如编辑器与导入器共享配置接口，接口的验证和提交语义需要共同确定，但两个入口仍可分别交付完整行为。共享基础的结束条件是消费者能取得并使用所需前提，不是所有消费者的业务都已实现。若一次改动在两处之间没有可用的中间状态，可以将这次改动共同实施，仍须保留各入口的行为义务与整体核对责任。

依赖的含义取决于消费者需要什么。接口语义稳定时，实现可以先行；只有服务、数据或整合提交可用后才成立的观察，仍等待对应前提。业务关联未必形成串行依赖。若未知会导致多方采用相互矛盾的共同语义，先形成可被采用的定义能减少返工；不依赖该未知的工作仍有推进价值。

局部排除说明生产范围，并没有修改整体承诺。延后义务有接手者，意味着责任已安置；完整结果取得适用依据，才意味着兑现。若原目标改变，决定的权限与影响又是另一项事实。

## 材料为何需要明确消费者

Issue description 帮助恢复当前目标、重要决定、依赖与开放责任；PR description 帮助判断候选及其证据范围。项目文档或可执行定义保存跨任务共同知识，packet 保存当前判断和下一步，讨论保存本次差异与决定的形成依据。动态答案在多个位置分别维护时，消费者可能取得不同版本；知识归属由可选的知识归属技能（按[技能入口](../SKILL.md#可选互补技能)发现）展开，任务材料由可选的 `svc-task-packet` 技能（按[技能入口](../SKILL.md#可选互补技能)发现）展开。

共享材料只有可发现、可取得且适用于当前成果，才能支持消费者继续工作。文件已写、已提交、已发布和已采用是不同事实。与成果一起取得的项目入口、共同定义和 packet 能降低重建上下文的成本；clone 外的正确笔记无法独自承担交接。Braid 父项正文也不会递归进入所有子项上下文，独立 clone 未必拥有最新共享实现。在内建 run 中，用 `braid object issue --parent NUMBER` 创建子项并在其正文保留需求、共同决定、依赖和交付 ref；创建未指派对象不会启动成员。root 等待成果时结束当前轮次，让出执行机会；反复轮询既不能替代交接，也可能占住成员所需的调度容量。并发参数限制在途 Braid 轮次，不限制 Pi 内部子任务、空闲原生会话或宿主总资源。

## 已有信息与具体未知

当前投影中的目标、正文和状态可以直接支持相应判断；重复获取同一信息未必带来新依据。投影可能折叠细节、截短正文或只保留讨论索引，通知也可能仅说明有新回复。信息是否足够，应由本次决定需要的事实区分：缺的是一段交接、当前候选、原文条件，还是实际结果。新的查询价值来自消除这个未知，而非开始或接续工作本身。

例行正文与讨论整理，目的是让既有决定和开放义务更易消费。具有整理能力的成员可以承担它；提出新解释、核实实现或结束产品义务仍需要对应判断与信息。方法入口的存在提供按需取得的能力，不构成每次工作都重读全部方法的理由。


## 核对成员实际执行与进展

先明确本次未知：是责任没有建立、执行失败、成员正在等待，还是实现与需求边界不符。对象的指派、open/closed、PR draft 或 head 都是协作事实，不独自证明对应成员正在执行、健康或已经完成。reviewer 也不等同于 PR 实施者；外部 review 请求与 Braid 原生执行须分别取证。

先从当前上游取得对象与候选身份。内建可用 `braid object --config PATH show NUMBER` 和 `context NUMBER`，候选差异可用 `diff NUMBER`；外部 GitHub 可用 `braid context issue --config PATH OWNER/REPO#NUMBER`、`braid context pr` 或原生 `gh` 读取当前正文、讨论及已发布 head/base。`braid status --config PATH --json` 提供实例和传输队列概况，不是逐成员存活查询；run 的 ledger 是独立实例状态，基础配置的 status 不能代替当前 run 快照。

使用已配置的 Console 时，`/api/harness/snapshot` 展示当前 Harness 的 assignments、sessions、turns、queue 与 worktrees；托管 run 时同时保留 runId，并读取当前 run ledger。根据 assignment 代次、session 与 turn 身份区分本任执行、旧任停止和尚未消费输入。该快照没有提供从每个工作项到执行全部身份的完整关联图；不能从数组顺序、时间接近或同一 profile 猜测责任归属。缺少连接事实时保留为未知，按实例记录与明确的 session/turn 身份定向取得证据。

快照的 observedAt 是查询时间，lifecycle 是 Harness 最后记录的状态；宿主意外退出后 running 可能陈旧，不能据此宣称进程存活。Console 的 runtime 状态、停止确认和 run 结果分别读取。OTLP 中按明确 session、turn 或 trace 关联的 provider 事件、工具结果和具体错误可补充执行观察；没有新观测不证明空闲，记录或 token 增长不证明产品进展。完整原生历史只用于当前问题的定向取证，路径及材料缺失仍是未知。

需要核对实现时，取得 PR 固定候选与实际改动。内建 diff 保留该次对象 revision 和 head/base，详情更新后需重新核对；外部 GitHub 用 `gh pr view NUMBER --repo OWNER/REPO --json headRefName,baseRefName,headRefOid,baseRefOid` 读取已发布身份。只有取得明确登记的 worktree 路径时，才按需用 `git --no-optional-locks -C PATH status --short`、`git --no-optional-locks -C PATH diff --stat` 及相关文件只读查看未发布工作。diff 不包含未跟踪文件内容，相关新文件要另行读取；运行中观察是当时截面，不是冻结候选。不要进入其它成员的修改、checkout、reset 或清理操作。

Pi 内部 subagents 与 background 工作不由 Braid 完整跟踪，沿其负责人保存的任务状态、日志与结果继续核实。原生局部委派不能替代应由独立 Braid 成员承担的 Issue/PR 责任；是否真的发生成员交接，需要子项指派、实际原生执行与可采用成果支持，建立子项、分派消息或 root 自己完成全部实现分别只证明对应动作。

判断有价值的新结果、明确阻碍或方向偏差后，在原工作项给出采用或纠偏决定；已有事实支持继续推进时可以等待。不为获得状态反复索取无动作回执，也不把局部错误直接当作整项失败。当前独立 Braid 没有 Factory 中的 `braid execution`、`braid pr review list` 等 CLI；未来能力变化以当前实际 help 和接口为准。
