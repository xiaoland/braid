# 编辑器与导入器共同修改设置

产品要求用户既能在编辑器修改设置，也能通过文件导入设置；修改后重新打开仍保留，无效修改不改变原状态。两条路径共享一份持久化配置。整体负责人需要取得的是两条路径都兑现这个完整承诺，而不是两份彼此独立的“保存成功”。

## 完整结果与局部分工

若配置接口已经稳定，编辑器和导入器可以分别实现并返回局部结果，整体负责人汇总重开与拒绝无效输入的行为。如果接口的验证和提交语义还没确定，先取得可被两方采用的共同接口及真实使用结果；业务实现可以准备不依赖该未知的部分，不能把未定义的事务含义各自猜成不同版本。

编辑器负责人排除导入器实现是合理的职责边界。它返回编辑器的实现和重开观察，同时指出导入路径仍需取得共享接口并核实失败时状态不变。整体负责人继续保留这项义务：导入器工作项明确采用接口并开始实施，或给回可用结果后，就有实际承接依据；只有建立关联和送达评论，还不足以结束这项交接。

如果接续任务只写“导入器调用接口并显示错误”，它的范围还没有包含无效输入不改变状态、导入后重开仍保留这两个完整结果。显示错误与这两个承诺具有不同依据；接手成立后，结果仍等候适用观察。

共同接口的现行约定在项目文档或可执行定义中保存，两项工作引用同一个地址和适用版本；各自 packet 保存当前工作与观察。一次关于边界的讨论解释这次决定，不再维护第二份完整合同。这样接续者能找到当前定义，而不用从几段旧讨论中猜哪次解释胜出。

## 变化会改变实际消费者的工作

实现中发现逐字段写入会在后续字段验证失败前改变部分状态，于是共同接口改为先验证整组，再一次提交。接口生产者发布了新定义与实现；编辑器已经采用它，导入器仍自行逐字段保存。发布成功只结束生产部分，导入器仍未采用足以保证无效输入不改变状态的结果。

整体负责人向导入器的当前实施者及其检查负责人说明新提交语义、旧路径失效的原因和采用入口。若检查已转交给另一人，只通知最初的 Issue 负责人就会遗漏真实消费者。导入器比较其代码和判据后改用共同接口，并返回无效导入前后状态相同的观察；这次后续行动支持采用成立，无需再发一轮“是否收到”。

接口后来要求调用者携带读取时的配置版本，以拒绝过期修改。服务端对含版本的请求检查通过，接口文档也已更新；审阅者仍从编辑器保存和导入动作核对真实请求，发现一个入口没有传入版本。漏传版本意味着该入口没有满足保护成立的条件，服务端的通过结果未涵盖它。补齐真实调用及该入口的结果，才可能支持两个入口都具备保护的结论；这个条件与是否同一人实现各层无关。

## 新约定按原承诺判断

导入器提议遇到无效字段时先保存有效字段，并把这项行为写入共同合同。原要求明确无效修改不改变原状态，发布合同或正确接续这个设计都不能解除冲突。原文使纠正约定及实现有了明确依据。如果某个检查原先提交了有效输入，修正该检查也可以合理；检查输入的问题与新约定的合法性由不同事实决定。

## 局部通过与整体接受分别判断

编辑器的有效结果可继续接受，但不证明导入后重开仍保留，也不证明无效导入保持原状态。整体负责人先消费两方已有结果，再按候选中共享接口的变化复查受影响行为，补导入路径仍缺的观察；不必因为提交号前移就拒绝所有旧证据或重复全部检查。

当两条路径的原承诺都有适用依据，候选完成整合，剩余讨论前提已解除，负责人可以完成交付判断。关联齐全或 PR 已合并本身不能替代这一比较；反过来，正确承接和有效观察已经成立，也不要求永久等待额外确认。

## 当前知识与维护结束

共同接口定义保存有效语义，任务材料保存实际候选、结论和证据入口。本次讨论围绕提交语义，问题有结论且其它未决事项已有独立责任时，历史前缀可以不再占用日常上下文；新的反例仍会产生新的工作。普通提醒、没有相关变化的提交和已消费的回执没有新的行动价值，维护已具备停止依据。
