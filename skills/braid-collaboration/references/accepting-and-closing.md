# 接受结论与结束条件

接受结论需要连接原承诺、现有判据、实际条件与候选结果。需求入口可定位、判据足够、观察已取得分别解决不同问题；一份映射、ready 状态或合并事实都没有独自回答其它问题。

## 新约定的成立依据

实现选择决定怎样兑现承诺，新默认行为或例外可能改变承诺本身。其成立依据是原要求的明确约束、适用条件和有权者的决定，而不是设计或合同已经发布。

明确违背原要求意味着约定及候选需要纠正；真正歧义涉及相应责任人的解释，目标改变还涉及授权范围。没有冲突的普通局部实现选择可以由实施者推进。把未裁决的新约定与已采用决定混为一谈，会让消费者正确接续一个尚未成立的解释。

检查输入或预期的修正，与产品约定的正确性也分别成立。某个用例选错了条件，并不证明候选的额外行为正确；修正该用例可以合理，同时仍存在需要纠正的行为。两项判断的依据不同，[共享设置例子](worked-example.md)提供具体反例。

## 声明范围与结果范围

PR 的行为声明及前序开放义务界定需要支撑的结果。用户入口、接口所需条件与可见结果之间的连接，决定局部实现是否兑现用户承诺；原要求中的连续操作和失败后状态也是结果的一部分。服务端结果可能有效，却没有涵盖调用者遗漏的条件。

派生矩阵、文案断言或已有检查集合，只表达和观察其实际包含的行为。集合全绿可以支持这些结果，未表达的原承诺仍缺依据。判据、条件与原始结果的关系由可选的 `svc-verification` 技能（按[技能入口](../SKILL.md#可选互补技能)发现）展开；检查数量、文件形式或审阅身份没有替代这种关系。

局部结果正确与整体尚欠可以同时成立。一个入口的通过不涵盖另一个入口，同一候选也可能因环境不同而有不同证据。修改后的旧观察是否仍适用，取决于行为、共享代码、数据、环境或判据受到的影响；普通 head 前移未必使全部证据失效，相同提交也未必使条件相同。

实际候选、原始输出及具体失败，使接受范围与剩余问题可以被检验。后续成功是新的结果，不改变首次失败的事实；执行前提受阻意味着尚未取得观察，不等于应用行为已经通过或失败。

## 局部合并与整体完成

ready 提出候选，merge 改变分支中的代码，Issue close 报告该项不再有待推进的义务。候选版本保护维持被接受对象的身份，不证明产品正确；操作回执才支持已合并或已关闭的状态事实。

有效局部成果可合并供后续开发，同时把尚欠消费者结果留在相应责任中。局部生产已经完成、成果可取得且后续责任有落点时，该局部工作也可以结束。整体完成则需要所有仍有效承诺的适用依据，或有权者已经改变目标；缺口无人负责、解释未决或关键观察尚欠，都意味着完成结论仍缺条件。

## 讨论整理与知识保留

讨论围绕具体问题展开，结束条件由该问题的未决义务决定。有效决定在消费者可取得的当前材料中保存后，历史讨论可以不再占用日常上下文；一个问题解决，仍不足以结束同一讨论中其它开放义务。

整理应先保存当前决定与开放义务，再使用当前上游实际支持的讨论能力。GitHub 的折叠、解决或隐藏有各自可见性影响；内建目前提供评论与回复，没有专用 resolve/hide 命令。不能把其它 Harness 的同名动作视为本项目能力。任何讨论整理都不会擦除已送达的原生历史，也不代表工作项完成。

自主 run 中 root 最后关闭：它会立即撤销整个范围的 writer 授权。子项仍有义务时提前关闭不会得到 completed，必须由操作者明确重开后才可继续。候选身份、范围义务和真实执行收尾支持的是运行闭环，业务正确性仍需实际消费者结果；本技能的完成判断不能被 run 终态代替。

没有新事实、决定、阻塞或行动价值时，维护可以停止。提醒说明有人提出检查请求，不说明被提醒者已经停滞。若由独立整理者维护 description 或讨论，它可以组织已有成立事实，缺失的产品依据与未决分歧仍归对应责任人判断。
