# Braid 协作

协作的目的，是让不同工作共同兑现产品承诺，同时使每位成员能够专心处理自己承担的结果。Braid 的工作项、讨论、指派与代码关联让事实可定位；成果是否可用、谁仍欠什么、哪些依据支持完成，是不同的判断。

## 适用边界与操作入口

本技能是可独立采用的协作方法，不依赖 Braid 安装，也不由 Braid 软件自动安装、加载或编译嵌入。使用者通过自己的 Agent Skills 发现入口按需读取本文件及相关 reference；不要将技能正文内联进 system、profile、role 或 task prompt。

Braid 软件接入 GitHub 与内建协作平台这两个同等角色的上游。`serve` 持续响应协作事件；`run` 在内建平台上让 root Agent 组织一次有限范围工作。内建平台不是运行模式，Web Console 属于整个 Braid。两种入口都需要按成果安置责任、采用真实候选及核对剩余义务；`run` 的 completed 不替代产品验收。

方法不授予创建、指派、修改、合并、关闭或调用模型的权限。按当前实例授权及实际接口操作：外部 GitHub 使用其原生入口与现有 `braid gh` 能力；内建使用 `braid object`。执行前按需查询当前 `braid --help` 和子命令 help。持有 Braid 源码时，可在仓库内读取 `docs/user-manual/local.md`、`docs/user-manual/run.md` 与 `docs/user-manual/console.md`，核对命令、配置及停止合同；未持有源码时，以实际安装版本的 help 和官方 `xiaoland/braid` 仓库中对应版本的文档为准。这些软件操作材料不是技能包的必需依赖，将本目录复制到其它 Agent Skills 环境仍可使用包内方法与 references。不要把其它 Harness 中同名工具或旧 CLI 能力当作本项目已有接口。

## 成果决定责任的边界

一个成果的意义取决于消费者用它完成什么。接口、调查或局部实现都可以成为有效交付；若用户结果跨越几个入口或共享状态，完整结果仍需要汇总责任。实现分工与整体责任可以不同：同一人实现各层，也可能遗漏真实调用；多个人分工，也可以兑现同一完整承诺。

Issue 组织一项结果的需求解释、方案、验收与剩余义务，PR 交付关联 Issue 可采用的实现候选。一个 Issue 可以组织多个 PR，一个 PR 也可以关联多个 Issue；关联本身不代替各项结果的责任。拆分结果责任与安排实施顺序是不同决定：共同基础先交付、业务 PR 顺序推进，不改变各业务 Issue 的结果责任。把能力分配给负责人、组织关联实现 PR、或调整共同前提时，读 [组织工作](references/organizing-work.md)。

## 生产、接手与兑现是不同事实

发布使成果可取得，采用使它进入消费者的工作，兑现意味着适用结果支持原承诺。文件存在、代码合并或消息送达分别只证明这些动作本身。消费者可发现的共同定义、任务材料与成果身份，使下一步有可靠依据；私有笔记即使正确，也未必可供接续。

接手安置了剩余义务的责任，没有解除其结果要求。延期的完整消费者结果仍包括原要求中的前态、动作和成功或失败后的状态；一个接口名或局部异常分支可能只表达其中一部分。实际后续工作能够支持承接成立，额外回执并不自然增加依据。成果取得、义务承接和变化影响的区别见 [交接与变化](references/handoffs-and-changes.md)。

## 共同约定与接受结论各有依据

原要求界定产品承诺，共同文档保存当前解释与实现合同。新默认行为或例外是否成立，取决于它与原承诺及适用条件的关系；文档发布本身没有改变目标的权限。明确冲突意味着约定或候选需要纠正，真正歧义与目标变化则涉及有权者的决定，普通实现选择仍由实施者判断。

行为声明的依据连接原承诺、判据、实际条件与候选结果。局部检查可以真实通过，却未覆盖用户入口所需的调用条件、连续操作或失败后状态。接受这样的局部成果与保留整体义务可以同时成立；变化后的旧证据是否有效，取决于受影响行为和观察条件，而非只有提交号。相关判断见 [接受与关闭](references/accepting-and-closing.md)，证据设计与解释可与 `svc-verification` 配合；发现方式见下文。

## 整理支持判断，也有自己的边界

Issue description 提供当前目标、采用的决定和开放义务，PR description 提供候选及其支撑范围；项目文档持有共同知识，packet 持有当前推理与接续状态。它们各有消费者与变化原因，重复维护同一动态答案会产生分歧。知识归属、任务维护及原生局部委派可分别参考环境提供的互补技能，不是使用本技能的前提。

已有上下文是否足够，取决于当前决定的具体未知。对象投影可以支持直接继续工作；折叠细节、新回复、责任冲突或候选身份缺口可能需要额外材料。例行整理可以由具有相应能力的整理者承担，它组织已成立事实和仍欠义务；事实正确性、需求解释与成果验收仍属于拥有相应判断责任和信息的人。更新的快照说明对象较新，不说明其中每项主张已被证实。

工作项状态、执行状态与产品进展各有依据。没有新评论或提交，不排除成员仍在处理未发布成果；执行中也不证明方向正确。需要判断其它成员（包括 reviewer）是否在推进、等待或失败时，先读 [执行与进展核查](references/organizing-work.md#核对成员实际执行与进展)，取得相应执行事实与产物证据。

讨论整理、局部合并、局部工作结束与整体完成分别改变不同事实。没有新的事实或行动价值时，维护可以停止；仍有效的义务不会因此消失。[编辑器与导入器的例子](references/worked-example.md)展示这些区别如何改变采用与结束结论。

## 可选互补技能

使用环境可能另外提供 `svc-verification`（证据与反馈）、`svc-documentation` 或 `svc-specs`（知识归属）、`svc-task-packet`（接续材料）、`svc-sub-agents` 或 `svc-agent-collaboration`（原生委派）。这些名称来自技能来源或不同环境，不保证均已安装，也不保证接口相同。需要时从当前 Agent Skills 清单按名称、description 与实际路径发现，再读取相应 SKILL.md；本目录不携带这些技能，不要求相邻目录，也不复制其正文。未提供时直接使用本技能已经说明的成果、责任、原始证据与剩余义务原则，并遵守当前项目维护规则。
