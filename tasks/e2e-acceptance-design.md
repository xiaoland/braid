# End-to-End Acceptance Design

- **Objective**: Define a complete black-box acceptance suite that can decide whether Issue/PR-native Human–Coding Agent collaboration is useful and mechanically trustworthy across discussion, autonomous implementation, review, lifecycle changes, synchronization faults, and process restarts.
- **Guardrails**: Exercise this project as a real self-hosted codebase with a genuine backlog Issue and merge intent, real GitHub, the real Wrapper process, a real Codex app-server/Coding Agent, and the Agent's real `gh` side effects. Do not manufacture a toy fixture or select a platform-incompatible project merely to obtain an Issue. A manually implemented bootstrap baseline and the candidate it creates must run from separately pinned worktrees/artifacts and may never be active on the same binding at once. Candidate promotion additionally requires a fresh installation and new binding; self-hosting cannot serve as its own proof. Destructive delivery, duplication, and restart cases use a disposable private mirror of the same pinned codebase. Use non-production credentials. Drive the system only through public binding/process controls and GitHub actions; judge it only through GitHub objects, refs, checks, rendered/raw comment bodies, timestamps, and documented public health surfaces. Do not use fake transports or Agents, inspect the Wrapper database, or treat unit/integration tests, internal logs, tool success, or Agent completion claims as acceptance evidence. Preserve the agreed authority split: provider owns thread data and resume; Wrapper owns only transport and mirror behavior.
- **Verification**: Every product promise maps to at least one executable journey with explicit actors, preconditions, stimuli, time bounds, external oracles, semantic Human-review questions, failure conditions, and retained GitHub evidence. The one real-project golden journey passes without operator correction, every repeated mechanical/adversarial journey passes, and all residual unavailable claims are reported rather than converted into success.
- **Current Truth**: Acceptance is self-hosted. An initial local bootstrap baseline `B` is implemented under the independent subdirectory and passes its developer guards, but is not accepted or externally provisioned. Once explicitly frozen, `B` is pinned by artifact/worktree digest, configuration digest, data directory, Worker identity, and exclusive Issue binding. `B` binds a genuine `xiaoland/svc` Issue whose only code scope is this independent subdirectory and whose real product objective is to improve the same transport through a real Draft PR. The Agent creates candidate Draft PR `C` from an independent target worktree. After `C` is locally viable, `B` is stopped before `C` is started against the same opaque Issue/thread binding so the source PR's actual review can continue through the capability being built; this is migration/dogfood evidence, not sufficient candidate acceptance. `C` must then be installed cleanly with a new binding in a disposable private mirror and pass the repeated full-stack adversarial campaigns before its source PR becomes Ready-for-review. The fixture needs two distinct trusted Human actors plus one untrusted Human actor, a separate Agent `gh` identity, a separate Wrapper App/bot identity, a real Cloudflare-backed webhook endpoint plus accelerated GraphQL reconciliation, and one real app-server provider pinned by version/schema digest. A run-scoped configuration shortens quiet and reconciliation clocks without changing their semantics. No external target, user-scope, GitHub, or Cloudflare mutation has yet been performed.
- **Next Step**: The local bootstrap implementation exists, but the campaign has not started. Continue in `tasks/bootstrap-implementation.md`; external user-scope, GitHub, Cloudflare, Issue, and candidate-worktree mutations require the separately announced exact mutation gate.

## Acceptance Boundary

A journey is end to end only when the actual GitHub service produces the stimuli and canonical state, the actual Wrapper observes and schedules them, the actual app-server/Coding Agent reasons and acts, and the actual GitHub service exposes the resulting comments, refs, PR state, reviews, and checks. Harness code may create fixtures, drive Human accounts, poll public APIs, record evidence, and stop/restart processes. It may not inject events below the GitHub boundary, replace the Agent, invoke Wrapper internals, or inspect local persistence to decide a pass.

## Proposed Journeys

1. **Golden autonomous collaboration and self-hosting**: Two Humans discuss the genuine associated-PR routing/publication Issue while pinned baseline `B` runs. After settling, the Agent may discuss but must not create a branch or PR until the missing choices are resolved without `@agent` or an imperative to start. The Agent creates linked Draft PR `C` in its independent worktree and implements the real feature under project governance. Once `C` is locally viable, the prescribed exclusive handoff stops `B` and starts `C` on the same opaque binding; subsequent PR review must arrive through `C`, steer the existing Agent thread, produce fixes, and preserve one canonical response plus FYI references. `C` records material design changes back on the Issue, provides repository-native verification evidence, and becomes Ready only after its separate fresh-binding candidate suite passes.
2. **Settling, urgency, and mixed surfaces**: Ordinary events repeatedly reset the quiet window and coalesce into one turn. A trusted `@agent` bypasses waiting, an untrusted mention does not, duplicate mentions do not create parallel turns, and active-turn input steers the same turn. When Issue and linked-PR surfaces participate, exactly one canonical mirror exists and every other participating surface has one deduplicated Wrapper FYI linking it; FYI events never wake another turn.
3. **Lifecycle and canonical freshness**: Create, edit, delete, minimize, and resolve controlled comments/review threads before and during a turn. The next observable Agent response and resulting diff use the latest canonical GitHub state, identify unavailable/deleted facts honestly, and do not continue applying superseded requirements. Activity resets settling without multiplying logical turns.
4. **Synchronization and idempotency**: Exercise normal webhook delivery, GitHub webhook redelivery, temporarily unavailable webhook ingress, accelerated GraphQL reconciliation, and delivery of an older event after a newer version. Each logical change affects the Agent at least once without duplicate logical turns or mirror comments; canonical latest GitHub state wins over arrival order.
5. **Process and transport continuity**: Restart the Wrapper while events are pending and while a turn is active; restart or temporarily disconnect app-server between turns; then add context-dependent GitHub input. Wrapper-owned delivery and mirror projections continue without duplicate remote side effects. The selected provider resumes the same bound thread through its public protocol. If provider status is unavailable, GitHub shows a neutral transport state rather than a fabricated Agent completion/failure, and Wrapper never creates a replacement thread.
6. **Turn mirror projection and limits**: Observe an actual long-running turn. The same canonical comment ID moves from a bounded visible processing state through periodic changed-body edits to the explicit final answer. The raw GitHub body contains only explicitly allowed protocol item types—such as reasoning summaries and tool items—in safely encoded hidden content; no raw-chain-of-thought item type is projected. Wrapper/Agent identities are not confused, no-op ticks do not edit, a lowered run-scoped shard threshold exercises multi-comment overflow, and interruption/failure/transport-unknown never masquerade as task success. This proves the Wrapper's projection allowlist, not any claim about provider-internal reasoning that its public protocol never exposes.

## Result Model

- **Mechanical result**: `pass`, `fail`, or `unavailable`, backed by URLs, node IDs, timestamps, raw and rendered comment snapshots, PR/Issue state, refs/SHAs, check results, and process-control timestamps.
- **Semantic result**: each Human independently records `acceptable` or `not acceptable` for premature action, readiness judgment, interpretation of the settled specification, response to steering, and clarity of the final evidence. Disagreement is not auto-resolved by the Agent.
- **Suite result**: pass requires the one self-hosted golden Issue-to-PR journey and prescribed `B -> C` exclusive handoff to pass without corrective operator intervention, plus three consecutive clean campaigns of every adversarial journey using clean `C` installations and fresh bindings against disposable private mirrors. Every mechanical assertion must pass and both trusted Humans must accept every semantic criterion. `Unavailable` is never counted as pass. The source-PR dogfood run and the fresh candidate runs are separate evidence; neither substitutes for the other.

## Timing Parameters to Approve

- Mirror tick: 5 seconds. A changed turn projection must be externally observable within 15 seconds; no-op ticks must not change the GitHub comment timestamp or digest.
- Quiet window in acceptance: 30 seconds. An ordinary turn must not expose a processing mirror before 30 seconds after the last relevant event and must expose one by 45 seconds, absent a recorded GitHub outage.
- Immediate `@agent`: a trusted mention must expose processing within 15 seconds, independent of the remaining quiet time.
- Reconciliation in acceptance: 60 seconds, distinct from the future production cadence. State missed by webhook must converge through settling and expose processing within 105 seconds of the GitHub mutation.
- These are pre-registered acceptance values, not production defaults. They may be tightened after baseline observation but may not be relaxed after a functional failure.

## Initial Event Matrix

- **Bound Issue**: body/title edit, close/reopen, and Issue-comment create/edit/delete; minimization or other lifecycle changes detectable only through canonical reconciliation remain in scope.
- **Natively associated PR**: PR body/state changes and `synchronize`; conversation-comment create/edit/delete; review submit/edit/dismiss; diff-comment create/edit/delete; review-thread resolve/unresolve; association addition/removal detected by webhook where available and canonical reconciliation otherwise.
- **Explicitly outside the initial wake contract**: raw repository `push`, labels, Projects, deployments, releases, and unrelated checks. The Agent may still query them through `gh`; adding them as wake sources requires a later acceptance change.
- **Origin rule**: Human-origin changes enter scheduling. Agent direct GitHub actions and Wrapper canonical/FYI projections remain externally auditable but are echo-suppressed and cannot recursively create turns.

## Evidence Bundle

Each campaign retains a manifest of fixture identities and pinned versions, Issue/PR URLs and node IDs, native association snapshots, comment IDs with raw and rendered bodies over time, webhook delivery/redelivery IDs available from GitHub, actor permissions, refs and SHAs, PR draft/ready transitions, review/thread states, check and seeded-verifier results, process stop/start timestamps, and both Human rubric forms. Private Wrapper storage, provider transcript, and internal logs may aid diagnosis after failure but are excluded from the pass oracle.

## Public Webhook Ingress

The zero-cost initial topology is `GitHub webhook -> Cloudflare Tunnel -> loopback-only local HTTP ingress -> Wrapper transport inbox`. Only the webhook listener is exposed; app-server, Wrapper control surfaces, and local files remain unreachable from the tunnel. The Wrapper validates GitHub's HMAC signature over the unmodified request bytes before parsing, then owns delivery deduplication and durable acknowledgement. Cloudflare performs no Issue/PR interpretation, scheduling, or Agent routing.

The default acceptance fixture uses a free Quick Tunnel and programmatically updates the dedicated test GitHub App's webhook configuration with its run-scoped `trycloudflare.com` URL; that App is installed only on the approved acceptance repositories. A Quick Tunnel restart yields a new URL and therefore requires another explicit webhook update. If the operator already controls a Cloudflare zone, a free-plan Named Tunnel with a stable hostname may replace it without changing the Wrapper contract. Workers, KV, D1, and Queues are not in the initial path: they would introduce a second persistence/retry authority that the PoC does not need.

Tunnel loss is a transport failure, not a quiet-window signal. GitHub does not automatically redeliver failed webhook deliveries, so canonical GraphQL reconciliation remains required and is the acceptance oracle for events missed while the local machine or tunnel is unavailable. Manual/API webhook redelivery is used only by the idempotency scenario.
