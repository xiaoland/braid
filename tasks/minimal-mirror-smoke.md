# Minimal Issue-to-Thread Mirror Smoke

- **Objective**: Prove one minimal real path in which a new GitHub Issue wakes one new Codex app-server thread and the Wrapper projects that turn into exactly one canonical Issue comment using only reconstructed assistant messages, provider-labelled reasoning summaries, and bounded mechanical tool-call summaries.
- **Guardrails**: Modify only `agent-handoff/` in the current bootstrap branch. Create no PR and permit no Agent code or Git mutation. Run the provider in a new dedicated smoke worktree/runtime with separate identity from the primary and bootstrap worktrees. Reuse only the dedicated test GitHub App credentials; expose only signed webhook ingress through a free temporary Tunnel. Never publish raw protocol events, raw CoT, commands, arguments, cwd/path, stdout/stderr, `aggregatedOutput`, tool results, environment, credentials, or the source GitHub comment snapshot. One Issue maps to one new provider thread; Wrapper never recreates provider context. The disposable Issue remains available for Human inspection after the run, while Wrapper, Tunnel, and webhook are stopped/disabled immediately after evidence capture.
- **Verification**: The runtime protocol-pin gate and local reducer tests first prove start/delta/completed coalescing, raw-field exclusion, count-or-maximum-age batching, terminal immediate flush, and no-op digest suppression. The external run then shows: one new Issue; one new provider thread; one Wrapper-owned logical mirror comment; visible processing state followed by the explicit final assistant response; raw comment content containing only the three sanctioned logical message kinds and bounded ownership metadata; no comment sharding; no self-echo turn; no PR, branch push, commit, or repository file change; and stopped Tunnel/webhook/Worker after capture. Record exact object IDs, timestamps, revision/edit count, decoded kind counts, body bytes, and residual unknowns without using unit tests as external acceptance evidence.
- **Current Truth**: The failed Issue 20 run and PR 21 are retired. Its recursive amplification mechanism and replacement reducer contract are preserved in [clean-baseline-and-projection-redesign.md](clean-baseline-and-projection-redesign.md) and [projection-reducer-contract.md](projection-reducer-contract.md). The minimum replacement slice is implemented: app-server lifecycle events reduce into one bounded logical history; raw reasoning and tool inputs/outputs are excluded; one comment contains directly readable, escaped JSON rather than base64 or shards; intermediate edits use completed-message count OR maximum dirty age; terminal flushes immediately; and a run-scoped read-only provider sandbox is available. All 92 child-project developer tests pass. A synthetic raw render is 813 bytes with four logical messages (`assistant_message`, `reasoning_summary`, `tool_call_summary`, final `assistant_message`), while raw-CoT, credential, command, cwd, plugin/script path, and aggregated-output sentinels are absent. The first external attempt on Issue 22 proved the projection contents but failed the one-turn invariant: reconciliation emitted a second turn/comment after 60 seconds because GraphQL reports an App actor as `svc-issue20-wrapper` while webhook/REST/config use `svc-issue20-wrapper[bot]`. Wrapper and Tunnel were stopped after two comments. Login normalization now treats only the exact `[bot]` suffix as the same mechanical identity; a live canonical read marks both existing comments `wake_eligible=false`. Issue 22 remains failed diagnostic evidence. The fresh Issue 23 retry passed the bounded objective: startup reconciliation created one provider turn and one Wrapper comment, terminal completion edited that same comment once, and more than one further reconciliation interval created no turn, comment, or edit. Both provider tasks are archived and all Worker/Tunnel processes are stopped. This smoke is not a resumption of full Issue-to-PR acceptance.
