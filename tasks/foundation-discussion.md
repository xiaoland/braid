# Foundation Discussion

- **Objective**: Establish the minimum high-level product and technical decisions needed to judge whether persistent GitHub collaboration can become the system of record for Human–Coding Agent work.
- **Guardrails**: Keep this project isolated inside `agent-handoff/`; treat the directory name as a working address rather than a product name; do not modify SVC framework sources; preserve comments as Human/Agent messages instead of commands or transport events; do not define acceptance or implementation work until the key product and technical choices are explicit; do not begin implementation without a new, scope-specific approval.
- **Verification**: The product authority, Agent agency, interaction timing, context ownership, GitHub lifecycle, trust boundaries, persistence ownership, and initial experiment boundary each have an explicit decision or a deliberately bounded open question; only then may the task advance to an acceptance scheme and implementation plan.
- **Current Truth**: The product is unnamed. Binding a Worker to an Issue grants the Agent a standing mandate to judge readiness and create a Draft PR without a separate command. Each Issue maps to exactly one long-lived Agent thread. The Coding Agent runtime or provider exclusively owns that thread's data, persistence, compaction, and resume behavior; the Wrapper holds only an opaque Issue-to-thread address and never reconstructs, replaces, or claims to recover thread context. Multiple candidate implementations and any one-to-many Agent architecture are explicitly deferred until there is evidence that they are needed; the current design does not pre-build that abstraction. GitHub is the collaboration authority and the Agent is the sole semantic decision-maker. The Wrapper neither creates PRs nor interprets Agent decisions; it wakes the Agent with GitHub comment/event links or IDs, while the Agent reads canonical state and performs GitHub actions through the GitHub CLI. Worktrees, branches, commits, PR creation, PR lifecycle decisions, and replacement are Agent-owned. The Wrapper does have transport-level PR awareness: it follows GitHub's native Issue-to-PR association and routes comments, reviews, and relevant events from every associated PR into the Issue's one Agent thread. It never selects an active PR or judges relevance; the Agent does. The Agent is durably instructed to associate every implementation PR with its Issue. This collaboration workflow—discuss in the Issue, implement when ready, associate and create a Draft PR, then continue through review—belongs in user-scope `AGENTS.md` so it survives compaction; an initial prompt only supplies the current Issue address and task context. The Wrapper does not encode the workflow as a semantic state machine. Its durable responsibility is limited to the opaque Issue-to-thread association, GitHub Issue/associated-PR synchronization and delivery facts, and turn-to-mirror-comment projection. It exposes comment edit, delete, hide or minimize, and review-resolution lifecycle changes to the same Agent thread, but does not rebuild linear context, generate reset-points, summarize superseded discussion, or create replacement threads. Coding Agent owns native compaction inside its existing thread. When the thread is idle, relevant GitHub events enter a mechanical settling queue and reset a quiet timer; after the quiet window, one wake turn receives the pending refs and the Agent still decides whether to speak or act. New events during an active steerable turn are injected immediately as opaque steer refs; if steering is unavailable they remain pending, and the Wrapper never forces an interrupt based on meaning. A Human comment containing the exact `@agent` mention is an urgent scheduling hint, not a command or authority grant. It starts immediately from idle or pending, steers the existing turn when steerable, and otherwise waits for the first safe steer or terminal boundary without a quiet delay; it never forces an unsafe interrupt or parallel turn. Duplicate hints coalesce. Webhook latency, reconciliation cadence, and the quiet window are separate clocks. The Wrapper passively mirrors each Agent turn rather than waiting for the Agent to deliver public messages: every five to ten seconds it mechanically edits one logical GitHub comment per turn, sharding only when the platform comment limit requires it. While active, the visible body only says that the Agent has seen the work and is processing it; protocol-visible turn messages, including tool calls, non-final assistant messages, and reasoning summaries, are retained in hidden comment content. Raw chain-of-thought is never mirrored. Hidden Markdown remains publicly retrievable despite being visually concealed. Structured interception of credentials, environment variables, and similar sensitive material is deferred; current LLM self-restraint is only best-effort mitigation, so the initial system consciously retains residual disclosure risk rather than claiming a security boundary. A mirrored comment follows the authoritative Agent protocol lifecycle: `inProgress` shows only the processing placeholder; `completed` publishes only an explicitly phased `final_answer`; a completed turn without one reports that no final response was produced; `interrupted`, `failed`, and transport-unknown each display their own neutral terminal or synchronization state. A steered turn retains its turn ID and logical comment, while interrupt followed by a new turn creates a new comment. Turn completion or failure never implies task completion, acceptance, or failure. Comments remain Human/Agent messages while webhook or polling records are transport signals. The foundation is closed, the end-to-end acceptance design is approved, and a separate bootstrap implementation plan is now the active task; no product implementation or external GitHub/Cloudflare provisioning has started.

## Design Closure Audit

- **Product authority resolved**: the Worker owner establishes or revokes a binding. Repository actors with `triage`, `write`, `maintain`, or `admin` permission may use `@agent` to spend immediate Agent capacity. Other actors' messages are still delivered with identity and permission metadata as untrusted collaboration input, but their mention does not bypass settling.
- **Routing association resolved**: the routing association is GitHub's native linked-PR relation established by the Agent through a closing keyword in a default-branch Draft PR body. A plain Issue mention or incidental cross-reference is insufficient, and the initial workflow permits exactly one bound Issue per implementation PR.
- **Publication resolved**: a mixed-surface turn has one canonical mirror comment on the most likely response surface. Every other participating surface receives one bounded FYI comment linking to that canonical comment and explaining that the turn combined events from multiple surfaces. The canonical target freezes when its comment is created and does not migrate when later events steer the active turn. The Wrapper chooses the target from an explicit structured Agent routing item, falling back deterministically to the trigger surface rather than interpreting prose. Each non-canonical participating surface receives at most one FYI per turn; FYI comments copy no Agent content, receive no progress edits, are deduplicated, and are suppressed as Wrapper-origin echoes. Because an FYI is neither Human prose nor Agent-authored prose, it is explicitly identified as a Wrapper reference message rather than impersonating either party.
- **Moves into acceptance design**: the disposable GitHub/provider fixture, exact event matrix, quiet-window values, `@agent` grammar cases, mirror cadence and sharding, webhook/poll duplication and ordering, process restarts, transport failures, and provider-owned thread resume behavior.
- **Moves into implementation planning**: local persistence schema, library choices, internal module layout, retry algorithms, and credential redaction beyond the explicitly accepted initial residual risk.

## Foundation Closure

- The decisions in this packet supersede conflicting exploratory statements in the initial brief: `@agent` is supported only as an urgent scheduling hint; Wrapper-managed reset-points and context reconstruction are withdrawn; provider-owned compaction/resume is authoritative; and the initial topology is exactly one Issue to one Agent thread, with multi-candidate or multi-Agent expansion deferred.
- Binding and revocation are explicit Worker-owner operations. All comments on a bound Issue and its associated PRs remain collaboration messages; immediate `@agent` scheduling is limited to trusted repository collaborators, while other actors' content remains attributable, untrusted input rather than disappearing.
- The initial routing oracle is GitHub's native Development/linked-PR relation, established by the Agent through a closing keyword in the Draft PR body against the default branch. Plain mentions, titles, branch names, and incidental cross-references are not routing authority. The initial workflow requires each implementation PR to link exactly one bound Issue.
- A mixed-surface turn produces one canonical Agent mirror plus bounded Wrapper FYI reference comments on other participating surfaces. Canonical selection may use an explicit structured Agent target, with a deterministic trigger-surface fallback; it never requires Wrapper prose interpretation.
- Product acceptance will be a real end-to-end black-box suite. Unit and component-integration tests may later protect implementation details but cannot substitute for acceptance evidence.
