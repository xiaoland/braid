# Codex app-server Protocol

This adapter targets the schema generated by the installed Codex binary, not a
hand-maintained protocol copy. The first verified version is
`codex-cli 0.147.0-alpha.6.5`; its stable v2 schema bundle has SHA-256
`7d79fe309dd7520843459070f3884ecf0e39cee2620c1c49aad6efb4eca76ecb`.
The experimental bundle required for Wrapper-origin application context has
SHA-256 `a14d4878fe7b8cdd31059dbca11d7167d8cfd06effa2f7991b5364439063a5c8`.
The executable schemas remain the authority when a later binary changes.

## Wire and Lifecycle

- stdio carries one JSON object per line. The Codex protocol deliberately omits
  the JSON-RPC `jsonrpc` member on the wire.
- A connection sends `initialize`, waits for its response, then sends the
  one-way `initialized` notification. Thread methods before initialization fail.
  This adapter explicitly opts into `capabilities.experimentalApi`; absence or
  drift of that capability is a startup failure, not a provenance downgrade.
- `thread/start` creates the provider-owned thread. `thread/resume` addresses the
  same provider thread after transport restart; an empty thread may not yet have
  a materialized rollout, so the bootstrap probe always completes a turn first.
- `turn/start` returns an in-progress turn handle. Live items arrive through
  notifications, and only `turn/completed` is terminal. Its status is one of
  `completed`, `interrupted`, `failed`, or `inProgress`; an `error` notification
  may be retryable and is not itself a terminal event.
- `turn/steer` has an `expectedTurnId` precondition. `turn/interrupt` must target
  the active turn; no active turn is a protocol error.
- Wrapper-origin wake references use experimental `additionalContext` entries
  with `kind: application`. Runtime verification found an undocumented
  non-empty `input` requirement, so each request also carries one fixed trigger
  text that explicitly identifies itself as Wrapper transport and says it is
  neither a Human message nor a command. It never contains GitHub prose. The
  application entry contains only a typed event/ref envelope; GitHub-authored
  content remains untrusted canonical state that the Agent fetches with `gh`.

The official app-server README documents the general lifecycle, while exact
fields and compatibility are pinned from `generate-json-schema` run against the
local binary: <https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md>.

## Mirror Projection Boundary

`item/completed` is the authoritative item snapshot for publication. Deltas are
live projections only.

- An `agentMessage` with phase `commentary` enters the visible chronological
  activity projection.
- An `agentMessage` with phase `final_answer` is a final-answer candidate. A
  same-turn steer can produce more than one such item before `turn/completed`;
  at terminal time the last completed candidate is the visible final answer.
- A `reasoning` item exposes both `summary` and `content`. Only `summary` may
  enter the mirror. `content` and `item/reasoning/textDelta` are raw reasoning
  and must never be published to GitHub.
- Tool and execution items use an explicit field allowlist. The renderer gives
  each logical call one Human-readable `<details>` block with bounded call and
  result evidence. Unknown item types or fields fail closed instead of being
  serialized wholesale.
- Completed-without-final, interrupted, failed, and transport-unknown are
  distinct outcomes. None is inferred to mean that the GitHub task succeeded or
  failed.

Provider thread history is intentionally lossy for some live item detail. The
Wrapper therefore observes live items for mirroring but never persists or
reconstructs the provider transcript and never owns compaction or resume.

## Executable Probe

Run the probe from the independent child project:

```shell
pdm run braid probe-app-server \
  --codex /absolute/path/to/codex \
  --workspace /absolute/path/to/a/read-only-probe-directory
```

The command generates and digests the installed stable schema, starts a
persistent read-only thread, observes an ordinary completion, proves that a
completed turn rejects steer, steers one active turn, interrupts another,
observes a real failed terminal state using a deliberately invalid model,
disconnects during an active turn without receiving a terminal event, restarts
the stdio process, confirms that the provider persisted that orphan as
interrupted, resumes the same thread, runs a final turn, and archives the probe
thread. It also proves that Wrapper-origin `application` context plus the fixed,
explicitly non-Human trigger can start and steer a turn. Success is one settled
JSON value; any missing method, unknown status, response mismatch, timeout, or
wrong final projection fails the command.
